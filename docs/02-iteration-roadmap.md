## 1. 计划目标

本计划将 VisionQC 从空仓库推进到一个可复现、可审计、可私有部署并可适配第二客户的企业级原型。迭代单位是“可演示的业务能力”，不是孤立技术组件。

每轮必须具备：

- 明确的业务结果。
- 可执行的验收场景。
- 自动化测试与运行证据。
- 已知限制和风险记录。
- 可回滚或不破坏前一轮能力的交付方式。

## 2. 交付策略

### 2.1 纵向切片原则

开发顺序遵循：

```text
可复现视觉基线
→ 单图推理服务
→ 人工复核与质量策略
→ MES/QMS 质量闭环
→ 可靠性、安全与可观测性
→ 第二客户适配
→ 私有部署与作品集交付
```

不采用“先做完所有后端，再做完所有前端，最后集成”的方式。每一轮结束时，系统都应比上一轮多完成一段真实业务链路。

### 2.2 风险优先级

优先消除以下风险：

1. 数据和模型无法在目标环境复现。
2. PatchCore 输出被误解为语义缺陷确认。
3. 阈值策略无法满足误放与误杀之间的业务平衡。
4. 外部写操作重试导致重复工单或重复暂扣。
5. 客户差异导致核心代码分叉。
6. 演示指标被误认为真实工厂生产指标。

### 2.3 计划假设

- 第一部署包为 `factory_a/transistor`。
- 第一模型为 PatchCore。
- 第一版仅使用研究/演示数据和 Mock MES/QMS。
- 第一版采用单仓库模块化单体，不拆微服务。
- PostgreSQL 保存业务状态；对象存储保存图片和热力图。
- 异步执行采用数据库 Outbox + Worker 或轻量任务队列。
- Docker Compose 为唯一支持的首版部署形式。

## 4. Iteration 0：需求冻结与技术基线

### 4.1 目标

将产品范围转化为可执行工程约束，消除数据、模型、硬件、许可证和接口方面的首要未知项。

### 4.2 需求范围

- OBJ-001 至 OBJ-006 的定义确认。
- OQ-001 至 OQ-006 的默认决策复核。
- 所有 P0 需求的责任模块和验收方式确认。

### 4.3 工作包

#### 产品与业务

- 审阅 PRD，确认第一产品类别为 `transistor`。
- 定义正常、灰区、高分异常三条演示样本路径。
- 固定第一版质量决策：放行、返工、报废、调查、无法判断。
- 形成“模型输出不是缺陷确认”的 UI 文案规范。
- 定义模拟工厂 A 的产品、批次、工位和用户角色。

#### 数据与 ML

- 下载并校验 MVTec AD 数据，记录来源、许可证和文件指纹。
- 建立不可变原始数据目录和派生数据目录规范。
- 生成 train/validation/test manifest，避免测试集参与阈值调优。
- 记录可用 CPU/GPU、内存和操作系统信息。
- 运行最小 PatchCore 技术探针，确认 Anomalib 与本地环境兼容。

#### 架构与工程

- 建立模块化单体目录方案。
- 决定 Python、Node、数据库和容器版本。
- 创建 ADR：模型边界、存储方案、异步方案、租户方案、认证方案。
- 定义核心 ID、时间、错误响应和 correlation ID 规范。
- 定义 Model Adapter、Policy、Connector 和 Deployment Pack 接口草案。

#### QA 与安全

- 建立风险登记表和需求追踪矩阵。
- 定义测试数据分级，禁止将未授权真实工厂数据加入仓库。
- 配置基础 secret scan、dependency scan 和 lint/type check。
- 定义发布时允许的漏洞例外流程。

### 4.4 交付物

- 批准或带有明确待办的 PRD v0.2。
- 数据集 manifest 和 SHA-256 清单。
- 至少四份 ADR。
- 初始仓库目录和开发环境说明。
- 风险登记表。
- 需求到迭代的追踪矩阵。

### 4.5 退出条件

- PatchCore 最小探针可读取一张正常图和一张异常图。
- 团队能指出数据集哪些部分用于适配、校准和最终测试。
- 所有 P0 需求有明确所属迭代。
- 无未记录的阻断性许可证或环境问题。
- 新成员可根据文档安装依赖并运行环境检查。

### 4.6 迭代演示

展示数据目录、固定样本、PatchCore 最小输出和架构决策；不要求完整 UI。

## 5. Iteration 1：离线视觉基线

### 5.1 目标

建立可复现的 PatchCore 适配、阈值校准、测试评测和模型打包流程。此阶段只解决“模型能否稳定给出异常分数和热力图”。

### 5.2 需求范围

- FR-ML-001 至 FR-ML-003。
- FR-EVAL-001、FR-EVAL-002。
- NFR-PERF-002 的基线测量。

### 5.3 工作包

#### 数据管线

- 实现 manifest 驱动的数据加载，不依赖目录隐式规则。
- 固定图片 resize、crop、normalize 等预处理。
- 对输入分辨率、类别分布和缺陷子类生成数据报告。
- 保存失败样本清单，不静默跳过损坏文件。

#### 模型适配

- 使用正常训练图片构建 PatchCore 特征库。
- 固定随机种子和依赖版本。
- 将异常分数统一映射到系统约定范围。
- 输出原图、异常图、叠加热力图和结构化 JSON。
- 对每次运行保存配置、代码 commit、硬件和运行时间。

#### 阈值校准

- 仅使用验证集选择 `review_threshold` 和 `hold_threshold`。
- 先约束缺陷误放率，再观察良品误杀率和复核比例。
- 输出阈值扫描曲线和混淆矩阵。
- 明确最终测试集在阈值确定后只运行一次正式报告。

#### 模型包

- 定义模型包目录：权重/特征库、预处理、metadata、metrics、license。
- 生成 `model-package.json`。
- 对模型包生成完整性哈希。
- 实现本地加载与一致性检查。

#### 测试

- 数据 manifest 单元测试。
- 预处理确定性测试。
- 同一模型包重复推理的一致性测试。
- 错误输入、缺失文件和不支持尺寸测试。

### 5.4 交付物

- `transistor` PatchCore 模型包 v1.0.0-rc1。
- 离线评测命令和机器可读评测结果。
- 人类可读评测报告。
- 代表性成功、误检和漏检样本集。
- 阈值校准报告。

### 5.5 验收标准

- 在干净环境中使用同一 manifest 可复现评测。
- 每张测试图片产生异常分数和热力图。
- 报告包含 image-level 指标、pixel-level 指标和选定阈值下的业务指标。
- 结果明确区分“异常定位”和“缺陷语义确认”。
- 模型包可独立校验来源、版本和数据指纹。
- 推理延迟在参考硬件上完成 P50/P95 测量。

### 5.6 退出门槛

如果模型无法在固定数据上稳定复现，禁止进入在线 API 开发；先解决数据切分、预处理或依赖问题。

### 5.7 迭代演示

命令行选择一张图片，输出异常分数、热力图、命中阈值和模型包信息；展示一个正确样本和一个失败样本。

## 6. Iteration 2：在线推理与持久化切片

### 6.1 目标

用户通过 Web/API 上传图片，系统完成校验、异步推理、持久化并展示结果。此轮不创建质量工单。

### 6.2 需求范围

- FR-ING-001 至 FR-ING-005。
- FR-ML-001 至 FR-ML-005。
- FR-AUD-001。
- NFR-PERF-001 至 NFR-PERF-004。
- NFR-REL-001、NFR-REL-002。

### 6.3 工作包

#### 后端

- 建立 FastAPI 应用、配置管理、数据库迁移和统一错误格式。
- 实现 `POST /inspections` 与 `GET /inspections/{id}`。
- 对租户内 `Idempotency-Key` 建唯一约束。
- 建立 Inspection、ImageAsset、InferenceResult 和 AuditEvent 表。
- 实现数据库 Outbox 和 Worker；任务状态可恢复。
- 将 Model Adapter 与业务服务解耦。

#### 存储

- 配置 PostgreSQL。
- 配置 MinIO 或兼容对象存储。
- 原图、热力图使用不同不可覆盖路径。
- 对文件计算 SHA-256，记录 MIME、尺寸和来源。

#### 前端

- 创建上传页面。
- 创建检测详情页面。
- 展示原图、热力图、异常分数、状态和模型版本。
- 提供任务轮询或轻量实时状态更新。
- 明确展示“异常不等于已确认缺陷”。

#### 平台与 QA

- Docker Compose 启动 API、Worker、PostgreSQL、对象存储和前端。
- 建立 API 集成测试和容器健康检查。
- 测试服务重启、重复上传、非法文件和模型超时。
- 建立结构化日志和 correlation ID。

### 6.4 交付物

- 可运行的端到端上传与推理系统。
- OpenAPI 文档。
- 数据库 ERD 初版。
- Docker Compose 开发环境。
- 上传与推理集成测试报告。

### 6.5 验收标准

- 合法图片上传后返回唯一 Inspection ID。
- 重复幂等键不产生第二次推理。
- 结果页面展示原图、热力图、分数、模型版本和耗时。
- API 或 Worker 重启后任务不丢失。
- 非法文件在调用模型前被拒绝。
- 日志可通过 correlation ID 串联上传、Worker 和模型调用。

### 6.6 退出门槛

数据持久化、幂等或重启恢复任一失败时，不进入质量策略开发。

### 6.7 迭代演示

上传一张正常图片和一张异常图片；展示异步状态变化、热力图和重复上传去重。

## 7. Iteration 3：双阈值策略与人工复核

### 7.1 目标

将模型输出转化为可控质量决策路径，支持自动放行、人工复核和高分暂扣，并保留完整人工责任链。

### 7.2 需求范围

- FR-POL-001 至 FR-POL-007。
- FR-REV-001 至 FR-REV-006。
- FR-TEN-001、FR-TEN-002。
- FR-AUD-001、FR-AUD-002。
- NFR-SEC-001、NFR-SEC-002、NFR-SEC-005。

### 7.3 工作包

#### 策略引擎

- 定义版本化 Policy Schema。
- 实现复核阈值和暂扣阈值校验。
- 实现安全降级：模型或策略异常时不自动放行。
- 保存 PolicyDecision 和策略快照。
- 为阈值边界、继承规则和冲突配置建立测试。

#### 人工复核

- 实现 ReviewTask 和 ReviewDecision。
- 实现任务认领、分配和乐观锁。
- 提供合格、返工、报废、调查和无法判断决策。
- 对高风险决策要求理由与二次确认。
- 将人工误检反馈写入独立反馈数据集。

#### 身份与权限

- 实现 MVP 身份认证和角色授权。
- 定义 `inspector`、`quality_manager`、`ml_engineer`、`admin`、`auditor`。
- 对前端路由和后端 API 同时执行权限校验。
- 建立跨租户与越权测试矩阵。

#### 前端

- 创建复核队列。
- 创建原图/热力图对比视图和透明度控制。
- 展示阈值、策略版本、批次和工位上下文。
- 提供高风险决策确认弹窗和明确影响说明。
- 状态不只使用颜色表达。

### 7.4 交付物

- 版本化双阈值策略。
- 人工复核工作台。
- RBAC 权限矩阵和自动化测试。
- 审计时间线初版。
- 人工反馈导出格式。

### 7.5 验收标准

- 低分、灰区和高分样本进入正确路径。
- 高分样本只暂扣，不自动报废。
- 两名质检员同时提交时只有一个决策成功。
- 决策记录包含操作者、理由、时间、模型和策略版本。
- 工厂 A 用户无法读取工厂 B 测试资源。
- 模型不可用时任务进入人工复核或失败队列，不自动放行。

### 7.6 退出门槛

任何可绕过人工确认的报废/返工路径，或任何跨租户数据泄露，均为阻断缺陷。

### 7.7 迭代演示

演示三张图片分别自动放行、进入灰区复核和触发暂扣；使用不同角色展示允许和禁止的操作。

## 8. Iteration 4：MES/QMS 质量闭环

### 8.1 目标

将人工确认的不合格结果安全写入模拟业务系统，形成从检测到质量事件关闭的完整链路。

### 8.2 需求范围

- FR-QC-001 至 FR-QC-007。
- FR-CON-001 至 FR-CON-007。
- FR-AUD-003。
- NFR-REL-002 至 NFR-REL-004。
- AC-E2E-001 至 AC-E2E-005。

### 8.3 工作包

#### 领域工作流

- 实现 QualityIncident、ExternalAction 和状态机。
- 定义批次暂扣、释放、返工、报废和调查的前置条件。
- 关闭事件前验证负责人、结果和验证记录。
- 实现内部事件时间线。

#### Mock MES

- 提供批次查询、暂扣、释放接口。
- 支持幂等键和可配置超时/失败注入。
- 保存调用记录用于对账。

#### Mock QMS

- 提供工单创建、查询、更新和关闭接口。
- 对幂等键返回已有工单。
- 支持“首次超时但服务端已创建”的测试模式。

#### Connector SDK

- 定义 `healthcheck`、`execute`、`get_status` 和错误分类接口。
- 区分可重试、不可重试和需要人工处理的错误。
- 建立共享合同测试套件。
- 实现有限重试、退避和人工重放。

#### 质量文档辅助

- 使用模板生成质量事件描述和复核清单。
- LLM 为可选增强，不得阻断闭环。
- 8D 初稿中的根因和措施默认标记为待调查。

#### 前端

- 创建质量事件页面。
- 展示外部操作状态、重试次数和外部工单号。
- 提供授权重放入口和理由字段。
- 提供完整检测到关闭时间线。

### 8.4 交付物

- Mock MES/QMS 服务。
- Connector SDK 与两个参考实现。
- 质量事件工作流。
- 外部操作对账与重放机制。
- 五个端到端场景测试。

### 8.5 验收标准

- 正常产品不创建质量事件。
- 人工确认异常后只创建一个质量事件和一个主 QMS 工单。
- 首次 QMS 超时后重试不产生重复工单。
- Connector 最终失败时事件保持可恢复状态，不伪装成功。
- 事件关闭前必须具有处置和验证记录。
- 时间线能还原模型、策略、人工和外部系统动作。

### 8.6 退出门槛

存在重复工单、错误自动关闭或无法恢复的外部动作时，禁止进入发布加固。

### 8.7 迭代演示

从异常图片开始，完成人工确认、批次暂扣、QMS 建单、模拟返工、验证和关闭；随后演示 QMS 超时重试且不重复建单。

## 9. Iteration 5：企业级加固

### 9.1 目标

验证系统在输入扰动、服务故障、越权访问、数据增长和运维操作下仍能安全、可观测并可恢复。

### 9.2 需求范围

- 所有 NFR-SEC、NFR-PERF、NFR-REL 要求。
- 可观测性、可维护性、可用性与无障碍要求。
- FR-EVAL-003、FR-EVAL-004、FR-OPS-001。
- AC-E2E-006。

### 9.3 工作包

#### 安全

- 完成跨租户读写、对象存储和导出测试。
- 完成文件伪装、超大图片、路径穿越和压缩炸弹风险测试。
- 配置依赖、镜像和 secret 扫描。
- 检查日志与错误响应中的敏感数据。
- 建立安全例外记录和发布阻断规则。

#### 可靠性

- 注入 API、Worker、数据库、对象存储、模型和 Connector 故障。
- 验证重启恢复、任务超时和人工重放。
- 实现失败任务隔离和运维处理页面。
- 执行备份与恢复演练。
- 增加对账任务，发现内部状态与 MES/QMS 不一致。

#### 性能

- 建立固定参考硬件基准。
- 测试并发上传、推理队列和看板查询。
- 记录 P50/P95/P99，区分冷启动与预热。
- 对热点查询增加索引并验证执行计划。

#### 模型鲁棒性

### 14.2 分支

- 主分支保持可运行。
- 每个需求或小型垂直切片使用短生命周期分支。
- 合并前必须通过 lint、type check、unit、integration 和必要的 model smoke test。

## 18. 评审与决策机制

### 18.1 每轮启动

- 确认依赖、风险和测试数据。
- 将需求拆为不超过 1-2 天的可验证任务。

### 18.2 每轮结束

- 现场运行演示，不使用预录结果代替验收。
- 展示成功路径和至少一个失败路径。
- 审阅自动测试和指标。
- 更新需求追踪、风险和已知限制。
- 只有达到退出条件才进入下一轮。

### 18.3 架构决策

以下变更必须记录 ADR：

- 引入新的数据库、消息系统或部署平台。
- 改变租户隔离边界。
- 允许新的自动业务操作。
- 改变模型输出语义或阈值策略。
- 将 LLM 引入质量决策路径。
- 改变审计数据保留与删除机制。

## 23. Iteration 8：工业边缘采集 Gateway

本轮把人工上传扩展为可部署在工厂工位旁的目录采集链路，保持质量工作流和租户边界不变。

### 23.1 交付范围

- 独立 `edge-gateway/` Python 工程，支持 PNG/JPEG 稳定文件检测、Deployment Pack 驱动的 Factory A/B 路径与命名规则。
- 本地 Pillow 安全解码、尺寸、模糊、过暗、过曝门禁；拒绝码、指标、隔离目录和 SQLite 审计。
- SQLite WAL + 原子 spool、内容 SHA-256、确定性幂等键、断网缓存、指数退避、进程重启恢复。
- 最小权限 `edge_gateway` JWT、Gateway heartbeat/status、后端工位状态 API 和前端积压看板。
- 目录/工业相机模拟器，覆盖正常、异常、损坏、过暗、过曝、模糊和重复样本。

### 23.2 退出条件

- Gateway 单元、集成、故障恢复和重启恢复测试通过；Factory A/B 配置与跨租户上传测试通过。
- 手动上传、多租户闭环、前端类型/组件测试和 Docker Compose 配置/冒烟不回归。
- 部署手册定义 demo/production 身份边界、备份、排障、指标和剩余风险；不引入 Kafka、Kubernetes 或真实 RTSP。
